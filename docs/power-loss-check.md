# Проверка устойчивости к сбою питания

Автотесты убивают процесс (SIGKILL), но кэш диска при этом не теряется. Эта инструкция проверяет настоящее жёсткое выключение: на виртуальной машине Linux (основной вариант) и, по желанию, на внешнем диске macOS.

**Убийство процесса и отключение питания — разные проверки.** Автотесты (`internal/folder/group_crash_test.go` и другие) убивают демон по `SIGKILL` на каждой фазе группы и проверяют восстановление, но данные в кэше ОС при этом остаются, и они не доказывают, что накопитель сбросил запись. Только настоящее выключение питания (или отключение накопителя) проверяет, что `fsync` / `F_FULLFSYNC` действительно дошли до носителя. Эта инструкция — вторая проверка, и её выполняет человек.

## 1. Что нужно

- Виртуальная машина Linux с файловой системой ext4 (VirtualBox, UTM, libvirt/virsh).
- Собранный бинарник `bin/sharedir-linux-amd64` внутри VM.
- Второй участник — лучше отдельная машина (например, ваш Mac): пир не должен выключаться вместе с VM. Второй экземпляр на той же VM не подходит.

## 2. Подготовка

1. На обеих сторонах создайте тестовую папку, например `~/sync-test`, и заполните её тысячами небольших файлов:

   ```bash
   mkdir -p ~/sync-test && cd ~/sync-test
   for i in $(seq 1 3000); do head -c 2048 /dev/urandom > "file-$i.bin"; done
   ```

2. Инициализируйте и сопрягите машины (ID показывает `sharedir id`, на обеих машинах):

   ```bash
   sharedir init --folder ~/sync-test
   sharedir pair ID_ДРУГОЙ_МАШИНЫ --addr IP_ДРУГОЙ_МАШИНЫ
   sharedir run
   ```

3. Дождитесь полной синхронизации: `sharedir status` должен показать, что всё синхронизировано, и хеши должны совпасть (см. пункт 5).

## 3. Нагрузка

На пире (не на VM) запустите цикл, который меняет существующие файлы и создаёт новые. Пока он работает, VM постоянно применяет входящие изменения:

```bash
cd ~/sync-test && while true; do f=$(find . -maxdepth 1 -type f | sort -R | head -1); head -c $((RANDOM * 4)) /dev/urandom > "$f"; head -c 4096 /dev/urandom > "new-$RANDOM-$(date +%s).bin"; sleep 0.1; done
```

Остановите цикл клавишами Ctrl+C.

## 4. Сбой

Во время нагрузки жёстко выключите VM без shutdown в случайный момент:

```bash
sleep $((RANDOM % 20 + 5)); virsh destroy ИМЯ_VM
```

В UTM или VirtualBox используйте «Power off» / «Выключить», а не «Shut down». Потом включите VM снова (`virsh start ИМЯ_VM` или кнопкой). Повторите 10–20 раз, каждый раз с новым случайным моментом.

## 5. Проверка после каждого включения

Сначала дождитесь, пока демон поднимется (около минуты), затем выполните проверки по порядку.

1. **Демон и статус.** Запустите `sharedir status`. Допустимы два результата:
   - обычная работа;
   - понятная остановка папки. Тогда запишите текст сообщения и токен из вывода.

2. **Хвосты операций.** Через несколько минут после запуска не должно остаться временных файлов старше нескольких минут и журнала операции:

   ```bash
   find ~/sync-test -name '.sharedir-tmp-*' -mmin +5
   find "$SHAREDIR_HOME" -name intent.json
   ```

   Обе команды должны ничего не выводить. Если `SHAREDIR_HOME` не задан, каталог настроек по умолчанию: `~/.config/sharedir` на Linux, `~/Library/Application Support/sharedir` на macOS.

3. **Совпадение хешей.** На VM и на пире выполните одно и то же, затем скопируйте один файл на другую сторону:

   ```bash
   cd ~/sync-test && find . -type f -print0 | sort -z | xargs -0 sha256sum > /tmp/hashes-$(hostname).txt
   ```

   На macOS `sha256sum` нет, используйте `shasum -a 256` вместо него. Сравнение:

   ```bash
   diff /tmp/hashes-ИМЯ_VM.txt /tmp/hashes-ИМЯ_ПИРА.txt
   ```

   Пустой вывод означает совпадение. Сравнивать нужно после остановки нагрузки и паузы синхронизации (около минуты).

4. **Лишние удаления и конфликты.** На пире не должно появиться лишних удалений и копий конфликтов без причины. Конфликтные копии содержат в имени `.sync-conflict-`:

   ```bash
   find ~/sync-test -name '*.sync-conflict-*'
   ```

   Если такие файлы появились, запишите, какие именно, и что меняли на обеих сторонах перед сбоем.

## 6. Что считать провалом и что прислать

Провал — любое из:

- демон не запускается или папка остановлена без понятной причины;
- остались `.sharedir-tmp-*` старше нескольких минут или `intent.json` после полного запуска;
- `diff` хешей не пустой;
- появились лишние удаления или конфликты без причины.

Пришлите координатору:

- вывод `sharedir status` (и `sharedir status --json`);
- лог демона: `journalctl --user -u sharedir --no-pager | tail -300`;
- список расхождений: вывод `diff` и `find`-команд из пункта 5.

## 7. macOS (по желанию)

Те же шаги на внешнем APFS-диске. Вместо отключения питания всей машины вытащите кабель диска во время синхронизации (во время применения входящих изменений), затем подключите снова. Здесь ожидаемо, что папка остановится («папка недоступна»): после подключения диска выберите «Оставить папку» (rebind) и только потом делайте проверки. Проверки из пункта 5 повторите, а вместо `sha256sum` используйте `shasum -a 256`.

## 8. Как устроена запись: что именно проверяется

Принятые от пира файлы применяются **группами** (до 64 файлов, 8 МиБ или 25 мс). Хранилище индекса — журнал `index.log` и снимок `index.snapshot` (gob) в каталоге настроек. Фазы одной группы:

| Фаза | Что происходит | Что остаётся после отключения питания в этот момент |
|---|---|---|
| G1 | Файлы группы записаны во временные `.sharedir-tmp-*` в папке; на каждый — `fsync`, на каждый подготовленный каталог — `fsync`, затем один `F_FULLFSYNC` на устройство (на Linux — только `fsync`). | Дерево и индекс не менялись; временные файлы удаляются при запуске. |
| G2 | Пишется `intent.json` (намерение группы) и сбрасывается на диск. | Есть намерение, дерево не тронуто или тронуто частично: при запуске группа откатывается или, если запись журнала уже есть, завершается. |
| G3 | Старые файлы переносятся в служебное место (capture), на их место ставятся новые; каталоги сбрасываются на диск. | То же: восстановление по `intent.json`. |
| G4 | В `index.log` дописывается один кадр с результатом всей группы, `fsync` (+ `F_FULLFSYNC` на macOS). Это точка публикации. | Кадр записан целиком — группа применена и долговечна; кадр оборван или не записан — группа откатывается. |
| G5 | Удаляются capture и `intent.json`, каталоги сбрасываются. | Остатки чистятся при запуске. |

**Гарантия:** при потере питания теряется не больше незавершённой группы. Опубликованная группа (после G4) долговечна, если накопитель соблюдает `F_FULLFSYNC` / `fsync`. Накопитель с недостоверным кэшем записи (некоторые USB-мосты, виртуальные диски с `cache=unsafe`) этого не обеспечивает, и провал на таком оборудовании — не ошибка sharedir. Для VM используйте режим кэша диска `writethrough`/`none`.

**Журнал и снимок.** Периодически (журнал 8 МиБ, 4096 изменений или сборка заметной части tombstone) журнал сжимается: пишется новый `index.snapshot` и сбрасывается на диск, затем создаётся новый пустой `index.log`. Отключение между этими шагами должно оставлять либо прежние снимок и журнал, либо новый снимок со старым журналом, чьи кадры пропускаются; потери и дубликатов записей быть не должно. Чтобы проверить сжатие, достаточно загрузки из п. 3 на несколько минут: журнал в такой нагрузке успеет вырасти до порога. Следите за размерами:

```bash
ls -l "$SHAREDIR_HOME"/index.snapshot "$SHAREDIR_HOME"/index.log   # по умолчанию каталог настроек, см. п. 5
```

**ACK удалений.** После применения удаления пир отправляет подтверждение (ACK). Tombstone собирается не раньше 30 суток и только после ACK всех устройств, поэтому за время проверки ни один tombstone не должен исчезнуть. Дополнительно проверьте удаление: на пире во время нагрузки удалите несколько файлов (`rm ~/sync-test/file-1*.bin`), выключите VM, включите её снова и убедитесь, что после синхронизации эти файлы отсутствуют на обеих машинах и не появились снова. Потеря ACK при отключении допустима: пир отправит его повторно.

**Дополнения к проверкам из п. 5.**

- После каждого включения остаётся допустимым только состояние «обычная работа» или понятная остановка папки (см. п. 5). Если в `sharedir status` появилась остановка `commit_failed`, пришлите текст и токен: это означает, что восстановление группы не удалось.
- `index.snapshot` и `index.log` не должны пропадать и не должны быть нулевого размера.
- Сравнение хешей из п. 5 — главный критерий: любое расхождение после паузы нагрузки — провал.
