# Протокол между устройствами, версия 2

Описано то, что реализовано в `internal/transport` (на момент конца этапа 04). Версия 1 не поддерживается: обратной совместимости и отката на v1 нет, обе машины обновляются вместе.

## 1. Транспорт и версия

- HTTPS со взаимным TLS 1.3. Доверие строится на ID устройства (SHA-256 сертификата), а не на CA. ID пира берётся только из сертификата, а не из JSON.
- Через relay идёт тот же протокол: relay только пересылает байты.
- Каждый запрос несёт заголовок `Sharedir-Protocol: 2` (`ProtocolVersion = 2`). Клиент также передаёт `X-Sharedir-Port` — порт, на котором он слушает, чтобы сервер знал обратный адрес пира.
- Если заголовок отсутствует или не равен `2`, сервер отвечает `426 Upgrade Required` с телом `{"code":"protocol_incompatible","expected":2,"received":"<что пришло>"}`. Для тел запросов `/files` и `/delta` с неверным полем `protocol` значение `received` равно `"body"`.
- Клиент превращает такой ответ в `*transport.ProtocolError`. Демон показывает пира со статусом `incompatible`, а в статусе пира выставляет `error_code = "protocol_incompatible"` и поля `expected_protocol` / `received_protocol`; приложение macOS и виджет Omarchy выводят понятную ошибку. Повторная попытка — через 60 секунд. Молчаливого сбоя и отката на v1 нет.

## 2. Порядок запросов

1. `POST /hello` — обязательное первое сообщение каждого TCP/relay-соединения. Сессия привязана к TLS-соединению; запрос любого другого пути без `/hello` получает `428 Precondition Required` (`hello required`). Сервер держит не больше 128 таких сессий (при переполнении старые вытесняются, нужен новый `/hello`).
2. `GET /index` — long-poll индекса пира.
3. `POST /files` (малые файлы пачкой), `GET /file` (файл целиком), `POST /delta` (изменённые блоки большого файла).
4. `POST /ack` — подтверждение удалений, нужно для сборки tombstone.

Сервер перед каждым ответом заново проверяет, что пир всё ещё сопряжён; иначе `403 access revoked` и закрытие соединения. Пока демон на паузе или папка остановлена, любой запрос получает `503 paused` (для `/index` и тел файлов — `folder unavailable`); клиент трактует это как «пир на паузе».

## 3. `POST /hello`

Тело — JSON не больше 64 KiB, неизвестные поля и лишний текст отвергаются:

```json
{"protocol":2,"storeEpoch":"…","peerSetEpoch":"…","features":["files","gzip","ack"],"limits":{}}
```

- `storeEpoch` — устойчивый идентификатор хранилища индекса (не меняется при перезапуске). Если хранилище пересоздано (например, `reset` остановленной папки), эпоха меняется.
- `peerSetEpoch` — номер состава доверенных устройств.
- `features` — сейчас `files`, `gzip`, `ack`. `limits` необязательно (в реализации пока не заполняется).
- Ответ `200` — такой же JSON сервера. Клиент проверяет, что `protocol` равен 2, иначе `ProtocolError`. Код ответа, отличный от 200 и 503, тоже даёт `ProtocolError`; 503 — «пир на паузе».

## 4. `GET /index`

Параметры: `since` (курсор), `epoch` (эпоха пира, которую клиент запомнил), `wait` (секунды ожидания, не больше серверного предела 50 с), `name` (если задан — вернуть только запись с этим именем, «точечное обновление»).

Ответ — JSON `IndexResponse`:

| Поле | Смысл |
|---|---|
| `protocol` | 2 |
| `storeEpoch` | эпоха хранилища пира |
| `cursor` | курсор, до которого ответ актуален |
| `reset` | `true` — это полный снимок (baseline), а не приращение. Сервер так отвечает, если эпоха клиента не совпала или его курсор уже сжат в снимок |
| `files` | записи `FileInfo` (имя, хеш, размер, вектор версии, признак удаления, `x` и т.д.); локальные поля (`Disk`) не передаются |
| `membershipEpoch` | номер состава устройств, только для аутентифицированного пира |
| `baselineChallenge` | токен проверки полного снимка, нужен для ACK (см. п. 8) |

Ограничения: тело ответа — до 512 MiB; имя — 4096 байт; вектор версии — 64 элемента; невалидный индекс отвергается целиком. Если эпоха хранилища на сервере поменялась между чтением и ответом, он отвечает `409 stale index`. Клиент ждёт заголовки до 60 с, общий срок long-poll — 70 с, простой без прогресса при чтении — 30 с.

**Повтор без сброса курсора.** Курсор на стороне клиента хранится по пиру вместе с эпохой. Сбой одного файла не сбрасывает его в 0 и не перезапрашивает полный индекс: запись остаётся в очереди и повторяется с экспоненциальной задержкой от 250 мс до 30 с (с небольшим разбросом). Если ответ `/files`, `/file` или `/delta` говорит, что версия изменилась или файла уже нет, клиент запрашивает `GET /index?name=…` и подставляет свежую запись, не трогая курсор. Полный индекс запрашивается только если сервер сам ответил `reset`.

## 5. `GET /file`

Параметры `name`, `hash`. Тело — байты файла целиком, `Content-Type: application/octet-stream`. Если хеш на сервере не совпал или файла нет, отвечает `409`:

- `version_changed` — запись с этим именем уже другая или удалена;
- `file unavailable` — файл сейчас недоступен;
- `503` — папка остановлена или на паузе.

Клиент превращает их в `ErrVersionChanged`, `ErrFileUnavailable`, `ErrPeerPaused`. Размер тела должен точно совпадать с объявленным, а при сжатии — считаться по распакованным данным.

## 6. `POST /files` — пачка малых файлов

Используется для файлов ≤ 256 KiB (в одной пачке — не больше 64 файлов и 8 MiB суммарно).

Запрос — JSON (до 256 KiB), `Accept: application/x-sharedir-files;version=2`:

```json
{"protocol":2,"items":[{"id":"0","name":"a.txt","hash":"<sha256>","size":123}]}
```

Лимиты: до `BatchMaxItems = 64` позиций, `id` и `name` уникальны, размер позиции ≤ `BatchMaxPlain = 256 KiB`, сумма ≤ `BatchMaxTotal = 8 MiB`. Нарушение — `400`.

Ответ — `Content-Type: application/x-sharedir-files;version=2`, один поток: магическая строка `SHDFIL02`, затем кадры, затем кадр-конец. Кадр: 4 байта длины заголовка (big-endian, не больше 4096), JSON-заголовок, тело.

Заголовок кадра (`BatchHeader`): `id`, `name`, `hash`, `status`, `size` (размер распакованного тела), `wireSize` (размер на проводе, не больше размера + 1024), `encoding` (`identity` или `gzip`). Статусы:

- `ok` — тело следует за заголовком;
- `version_changed` — версия на сервере другая;
- `not_found` — файла нет или он удалён;
- `blocked` — папка остановлена или на паузе.

Последний кадр: `{"end":true,"count":N}`. Клиент принимает поток только полностью: обрыв до кадра-конца — ошибка, не тихий EOF. Позиции, которые уже пришли, повторно не запрашиваются: после обрыва клиент повторяет запрос только по недостающим `id` (задержка 250 мс → 30 с), не сбрасывая курсор индекса.

## 7. `POST /delta` — большие файлы

Применяется, если на приёмнике есть предыдущая версия файла (база) и размер новой версии не меньше 8 MiB (`DeltaMinSize`) и не больше 65536 блоков по 1 MiB (`DeltaMaxBlocks`, `DeltaBlockSize`).

Запрос (JSON, не больше 5 MiB):

```json
{"protocol":2,"name":"…","targetHash":"…","targetSize":N,"baseHash":"…","baseSize":M,"blockSize":1048576,"blocks":["<sha256 блока базы>", …]}
```

Ответ — `Content-Type: application/x-sharedir-delta;version=2`: магическая строка `SHDDEL02`, затем заголовки с 4-байтовой длиной, как в п. 6.

1. Первый заголовок — `status`:
   - `ok` — дальше идут изменённые блоки;
   - `version_changed` — целевая версия на сервере другая;
   - `full_required` — изменилось 70% или больше размера файла; клиент скачивает файл целиком через `/file`.
2. Для каждого изменённого блока — заголовок `offset`, `length`, `hash`, `encoding` (`identity`/`gzip`), `wireSize`, затем тело блока.
3. Завершающий заголовок `{"end":true,"targetHash":…,"targetSize":…,"frames":N}`.

Клиент собирает новый файл во временной области и проверяет хеш каждого блока и итоговый хеш; результат публикуется как обычная версия только после проверки. Если база изменилась или приёмник не может применить дельту, он скачивает файл целиком. Сервер хеширует целевой файл до отправки и сверяет `stat` до и после, поэтому изменение файла во время передачи даёт обрыв ответа, а не испорченные данные.

## 8. `POST /ack` и сборка tombstone

Tombstone (запись об удалении) собирается, только когда прошло 30 суток с момента, когда удаление было замечено, и все известные устройства подтвердили именно эту версию удаления. Устройство шлёт ACK после того, как применило удаление у себя. Подтверждение:

```json
{"storeEpoch":"…","membershipEpoch":N,"baselineChallenge":"…","deletions":[{"name":"…","version":{"<ID>":N}}]}
```

- Тело — до 1 MiB; до 256 удалений за запрос; `version` — не больше 64 элементов.
- `baselineChallenge` сервер выдаёт в `/index` вместе с `reset: true` (полный снимок с удалениями) и привязывает его к курсору и эпохе пира. Подтверждение с токеном фиксирует, что пир получил полный снимок целиком: только после этого он считается участником сборки.
- Ответ `204` — принято; `409 stale ack` — эпоха, состав устройств или токен устарели (клиент получает `ErrStaleACK`, сбрасывает накопленные ACK и заново запрашивает полный снимок); `403` — сертификат не принят или в сессии нет `storeEpoch`; `400` — неверное тело; `503` — не удалось сохранить.
- После успешного ACK сервер запускает сборку (`CollectTombstones`). Собранная запись заносится в список «снятых» версий (`Retired`): такая версия удаления остаётся известной навсегда, поэтому устаревшая копия не воскресит файл.

## 9. Сжатие

- gzip включается по блоку, и только если первые 32 KiB сжимаются не хуже чем на 12,5% и тело не меньше 1 KiB. Заведомо несжимаемые типы (`knownIncompressible`: `.jpg`, `.jpeg`, `.png`, `.zip`, `.gz`, `.mp4`) не сжимаются.
- В `/files` клиент всегда передаёт `Accept-Encoding: gzip`, и сервер решает по каждому кадру, поэтому кадры могут идти сжатыми и в LAN. В `GET /file` и `/delta` клиент просит gzip только при подключении через relay (`addr` равен `relay` или `relay:…`), в прямой связи — `identity`.
- Хеш в заголовках кадров — всегда SHA-256 распакованного содержимого; размер после распаковки жёстко ограничен объявленным.

## 10. Таймауты и ограничения

- TLS handshake и заголовки: 5 с; keep-alive простой: 90 с.
- Простой записи/чтения без прогресса: 30 с; общая длительность передачи файла не ограничена.
- Одновременных входящих соединений: 128 всего (TCP и relay вместе), прямых TCP — 16 на IP, relay — 64.
- Лимиты relay описаны в README.
