# 04 — скорость синхронизации и износ SSD

Повод: первая синхронизация 2092 мелких файлов идёт со скоростью 3–8 файлов/с; запись на диск на порядки больше объёма данных.

## Диагноз (код на main после этапа 03)
- Каждый принятый файл — отдельная транзакция `commitLocked` (`internal/folder/commit.go`): flush файла, durable intent, flush каталогов, **полная перезапись `index.json`** (`persistLocked`, ~330 байт на файл, сейчас ~0,3–0,7 МБ) и `F_FULLFSYNC`, затем удаление intent и снова flush каталога. Несколько `F_FULLFSYNC` и O(N) байт на каждый файл → O(N²) записи за первую синхронизацию.
- `ApplyRemote` применяет шаги строго по одному (`internal/folder/apply.go`), каждый файл — отдельный HTTPS-запрос `/file`.
- Сбой одного файла → `since = 0`, пауза 5 с, повторный полный индекс (`internal/app/daemon.go`).
- Неудачные переподключения не логируются (только первый обрыв, `wasConnected`), простой выглядит как зависание.
- Уже исправлено этапом 02: Scan сохраняет индекс только при изменениях (`dirty`), есть кэш хэшей, загрузка идёт вне `scanMu`.

## Решения владельца (2026-11-04)
1. Делать все пункты ниже, включая параллельную загрузку.
2. Индекс — собственный append-only журнал изменений + периодический компактный снимок (без новых зависимостей). Меняет стек в `PLAN.md`.
3. Протокол между пирами меняется **без обратной совместимости**: обе машины обновляются одновременно. Несовместимый пир — понятная ошибка в Status/меню/виджете, а не молчаливый сбой.
4. Встроенные исключения: временные файлы редакторов/офиса/браузеров и `node_modules`, `.venv`, `__pycache__`, `.next`, `dist`. `.git` **не** исключается.
5. «Объединить этапы» — этап 02 уже закрыт, объединять нечего; всё делается одним этапом 04.

## Требования (вход для проекта 04-01)
Сохранение и flush
- R1 Групповой commit: много входящих файлов — одна транзакция (один intent, одна запись журнала, один набор flush), с ограничением по числу файлов/байт/времени. Гарантии сбоя питания из `plan/design/folder.md` и `docs/power-loss-check.md` сохраняются.
- R2 Индекс: журнал + снимок, компактный бинарный формат (gob и сжатие из stdlib), миграция из `index.json`, сжатие журнала по порогу.
- R3 `F_FULLFSYNC` только там, где нужен: на точке durable commit группы и снимка; где достаточно порядка — `F_BARRIERFSYNC`. Обосновать каждую замену.
- R4 Служебные поля (lastScan и т. п.) не вызывают записи.
- R5 Сборка мусора tombstone: после подтверждения всеми пирами и срока хранения.
Скан и watcher
- R6 Не запускать Scan на собственные записи демона.
- R7 Инкрементальный скан по путям из событий FSEvents/inotify; полный обход — периодический и при переполнении/потере событий.
- R8 Ожидание стабильности файла (size+mtime не меняются N секунд) перед публикацией.
- R9 Периодический полный скан раз в 10–15 мин при рабочем вотчере (раз в минуту — без вотчера).
- R10 `scanMu` не удерживается на обходе и хэшировании; commit с перепроверкой stat.
Сеть
- R11 Параллельная загрузка 4–8 файлов (HTTP/2 уже включён), настраиваемо.
- R12 Пакетная выдача мелких файлов одним потоком (`/files`).
- R13 Повтор только упавших файлов, без `since = 0` и полного индекса.
- R14 Сжатие на лету для сжимаемых файлов через relay (stdlib).
- R15 Версия протокола в рукопожатии, ошибка несовместимости в Status.
Меньше перезаписи файлов
- R16 Клонирование по хэшу (`clonefile` APFS, `FICLONE` btrfs, иначе копия) при переносе/копии; пропуск загрузки при совпадении локального содержимого.
- R17 Дельта-передача больших файлов (блочные хэши, запись только изменённых блоков в клон).
Прочее
- R18 Расширенные встроенные исключения (решение 4).
- R19 Логи: ограничение размера, дедуп повторов; неудачные переподключения — раз в N минут.
- R20 Измеримая приёмка: тест/бенчмарк синхронизации ≥2000 мелких файлов между двумя in-process демонами со счётчиками байт записи индекса и числа flush (через persistHooks), пороги заданы в проекте.
