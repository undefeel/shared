# Ревью 01-01: сеть и криптография

Проверены `internal/identity/`, `internal/transport/`, `internal/discovery/`, три файла `internal/relay/`, `internal/app/relay.go`, `cmd/sharedir/relay.go`, unit systemd и сетевые вызовы демона. Находки ниже подтверждены путями исполнения; временные тесты не создавались.

### 01-01-01 [high] Удаление сопряжения не отзывает доступ по открытому соединению
- Где: `internal/transport/transport.go:50`, `internal/transport/transport.go:94`; `internal/app/daemon.go:615`, `internal/app/daemon.go:315`.
- Сценарий: сопряжённый клиент открывает TLS, затем владелец выполняет Unpair → клиент продолжает запрашивать `/index` и `/file` по keep-alive соединению и читать новые изменения после отзыва доверия. Это работает и внутри relay.
- Доказательство: ServerTLS вызывает allowed только в VerifyPeerCertificate при handshake. Handler проверяет Paused, но не актуальное сопряжение. Unpair удаляет запись и вызывает syncPeers; тот отменяет только исходящий runPeer, не входящие соединения сервера. Таким образом следующий HTTP-запрос по существующему TLS снова попадает в file/index без проверки isPeer. Reload с удалённым пиром имеет тот же эффект.
- Исправление: проверять текущее разрешение по сертификату на каждом запросе в transport.Handler; для немедленного прекращения уже текущей передачи учитывать соединения/контексты по ID и закрывать их при отзыве в app. Проверять разрешение повторно после long-poll перед выдачей индекса.
- Уровень исправления: L3.

### 01-01-02 [high] Любой TCP-клиент может бессрочно занимать соединения и горутины до проверки сертификата
- Где: `internal/app/daemon.go:175`, `internal/app/daemon.go:180`; `internal/transport/transport.go:50`.
- Сценарий: посторонний хост открывает много соединений на 22100 и не отправляет ClientHello → демон держит сокет и обслуживающую горутину для каждого, пока атакующий не закроет их или процесс не исчерпает ресурсы. Сопряжение и приватный ключ не нужны.
- Доказательство: HTTP Server создаётся без ReadHeaderTimeout, ReadTimeout, WriteTimeout и без ограничения входящих соединений; TLS listener принимает TCP лениво, handshake выполняется HTTP-сервером при обслуживании. При нулевых таймаутах сервера нет дедлайна handshake. VerifyPeerCertificate ещё не вызван, поэтому allowed не защищает этот путь. Аналогично уже аутентифицированный клиент может зависнуть на чтении заголовков/записи ответа. Входящие relay-каналы поступают тому же серверу; client.Listen принимает incoming без проверки From, поэтому владелец общего relay-токена может также открыть канал и молчать перед внутренним TLS.
- Исправление: задать таймаут заголовков/handshake и лимит принятых соединений в app; для длительной передачи файлов использовать отдельную политику прогресса/idle deadline, совместимую с long-poll. Ограничить одновременно принимаемые relay-каналы.
- Уровень исправления: L2.

### 01-01-03 [medium] Неограниченные таблицы обнаруженных и отклонённых устройств
- Где: `internal/discovery/discovery.go:142`, `internal/discovery/discovery.go:165`, `internal/discovery/discovery.go:184`; `internal/app/daemon.go:296`.
- Сценарий: LAN-клиент отправляет небольшие валидные UDP-анонсы с разными каноническими ID → память растёт без ограничения даже после истечения 90 секунд. Второй путь: несопряжённый TCP-клиент предъявляет новые сертификаты, и rejected навсегда сохраняет каждый ID в incoming.
- Доказательство: recvLoop ограничивает пакет буфером 2048 байт и валидирует Normalize, но без проверки владения ключом записывает каждый ID в devices. TTL проверяется только при Lookup/Devices, удаления записей нет. Нападающий может генерировать ID просто из любых 32 байт; сертификаты для UDP не требуются. В TLS-пути ServerTLS вызывает onReject для каждого нового отпечатка; rejected добавляет Candidate в incoming без лимита/TTL, очистка предусмотрена лишь для конкретного сопрягаемого ID. Status затем перебирает эти таблицы, увеличивая также затраты CPU/UI.
- Исправление: ограничить обе таблицы, удалять истёкшие записи, добавить ограничение частоты приёма по источнику и глобально. Не связывать лимит памяти только с размером одного пакета.
- Уровень исправления: L2.

### 01-01-04 [medium] Индекс пира декодируется без лимита памяти и длины полей
- Где: `internal/transport/transport.go:210`, `internal/transport/transport.go:219`.
- Сценарий: скомпрометированный сопряжённый пир отвечает HTTP 200 на `/index` и быстро передаёт огромный JSON с массивом files или очень длинным name/вектором версий → получатель расходует память до OOM до начала проверки путей.
- Доказательство: Index передаёт resp.Body непосредственно json.Decoder.Decode(&out); нет ограничения байтов, числа записей, длины строк или векторов. Таймаут 70 секунд ограничивает время, но не количество принятых байтов. `folder.ApplyRemote` проверяет validName только после полного декодирования (apply.go:111–115). Подделка UDP/чужой сертификат этот путь не открывают: нужен уже доверенный ключ.
- Исправление: добавить ограничение размера ответа с обнаружением превышения, лимиты полей и записей; для больших папок предусмотреть пагинацию/потоковый ограниченный протокол в transport и согласовать ограничения с folder.
- Уровень исправления: L2.

### 01-01-05 [medium] Загрузка файла не ограничена размером и не имеет таймаута прогресса
- Где: `internal/transport/transport.go:164`, `internal/transport/transport.go:225`; смежное подтверждение `internal/folder/apply.go:280` и `internal/app/daemon.go:506`.
- Сценарий: сопряжённый пир сообщает маленький файл, затем отвечает бесконечным chunked body → временный файл заполняет диск. Либо пир присылает заголовки и перестаёт передавать данные → последовательный runPeer застревает на этой загрузке до ручной отмены/ошибки TCP, не переходит к другим файлам и адресам.
- Доказательство: Fetcher вызывает get с долгоживущим контекстом runPeer, затем io.Copy(w, resp.Body), не используя fi.Size. HTTP Client не имеет Timeout/ResponseHeaderTimeout; TLSHandshakeTimeout относится только к handshake. folder.download пишет поток в CreateTemp через MultiWriter и проверяет хеш лишь после возврата fetch; поэтому проверка хеша не ограничивает заполнение диска и не помогает при незавершённом теле. При обычном обрыве fetch возвращает ошибку и tmp удаляется, но до обрыва ограничений нет.
- Исправление: проверять неотрицательный заявленный размер и копировать не более размера плюс один байт с ошибкой при превышении; добавить дедлайн ответа и idle/progress timeout передачи, отменять запрос при отсутствии прогресса. Согласовать лимиты в transport.Fetcher и folder.download.
- Уровень исправления: L2.

### 01-01-06 [medium] После проверки общего токена relay снимает все глобальные лимиты соединений
- Где: `internal/relay/server.go:169`, `internal/relay/server.go:185`, `internal/relay/server.go:229`, `internal/relay/server.go:299`; `deploy/sharedir-relay.service:14`.
- Сценарий: пользователь общего relay-токена создаёт много сертификатов и регистрирует listen либо открывает множество полностью связанных туннелей → исчерпывает FD/память VPS и блокирует остальных пользователей relay.
- Доказательство: maxPreAuth/maxPreAuthPerIP учитывают соединение лишь до leavePreAuth на строке 170. listeners имеет по одному элементу на произвольный отпечаток, общего лимита нет. maxPending=64 относится только к незавершённым connect одного from; после accept запись удаляется и pipe не учитывается ни в одном лимите. В pipe нет idle/lifetime deadline. Поэтому даже одна пара сертификатов может последовательно создавать неограниченное число активных туннелей. Unit разрешает 65536 FD, не задаёт MemoryMax/TasksMax специально для сервиса; песочница доступа к файлам не ограничивает этот сетевой расход.
- Исправление: учитывать глобальные и per-ID активные управляющие соединения, pending и туннели до их фактического закрытия; ограничить скорость создания и простой. Добавить ресурсные ограничения systemd как второй рубеж.
- Уровень исправления: L2.

### 01-01-07 [medium] Гонка accept с таймаутом оставляет принятый relay-сокет без владельца
- Где: `internal/relay/server.go:257`, `internal/relay/server.go:268`, `internal/relay/server.go:282`.
- Сценарий: accept приходит на границе 15-секундного ожидания connect → serveAccept успешно извлекает pending, но serveConnect выбирает timeout и возвращается; принятый сокет навсегда остаётся в канале без читателя и закрытия.
- Доказательство: serveAccept под mutex получает p и удаляет его из map (284–286), затем вне mutex делает `p.ch <- conn` в буфер ёмкостью 1 и возвращает true. Между извлечением p и отправкой serveConnect может получить таймаут (270–272), выполнить defer delete и закрыть исходный conn через handle. Отправка accept всё равно успешна, keep=true запрещает handle закрывать accept-сокет. Даже при уже заполненном p.ch select может выбрать одновременно готовый timer. У accepted conn дедлайн снят строкой 171; ни pipe, ни другого владельца для его закрытия не создано. На клиенте open позже истечёт по дедлайну, но сервер в этот потерянный сокет уже никогда не читает и не пишет, поэтому FIN сам по себе не освобождает серверный FD.
- Исправление: атомарно согласовать переход pending в accepted/expired, передавать владение сокетом только выигравшему connect; при отмене/таймауте явно закрывать поздний accept и дренировать уже доставленный канал. Добавить конкурентный регрессионный тест с управляемым временем/барьерами.
- Уровень исправления: L2.

## Проверенные защитные свойства и границы

- transport.ServerTLS требует клиентский сертификат и проверяет полный SHA-256 ID по актуальному конфигу при handshake; transport.NewClient сравнивает полный ожидаемый ID. Оба требуют TLS 1.3. `InsecureSkipVerify` в transport и relay client компенсирован собственной проверкой полного отпечатка, обхода чужим сертификатом не найдено.
- Ключ Ed25519 генерируется crypto/rand; новый key.pem создаётся с 0600, cert.pem — 0644; сертификат на 30 лет. Стандартная PKI-проверка срока отсутствует при pinning: это свойство модели ключа, само по себе не доказательство обхода сопряжения.
- UDP-анонс не вызывает Pair. Адрес берётся из IP отправителя и валидного порта, не из произвольной строки payload. Подмена анонса меняет адрес попытки, но не ожидаемый TLS ID. Устройство отвечает на Ask без rate limit; размер пакета при чтении ограничен 2048 байт. Масштаб отражённой атаки отдельно не измерялся.
- Relay проверяет общий токен constant-time до обработки операции, выводит ID из сертификата, проверяет p.to при accept; session генерируется из 160 случайных бит. Кадр JSON ограничен 4096 байт и hello — 10 секундами. Сам VPS видит метаданные и может оборвать/задержать связь; данные защищены внутренним mTLS между устройствами. Один transport.Client с тем же ожидаемым ID используется и после перехода relay → LAN.
- При обычном обрыве pipe закрывает обе стороны и ждёт копирующие горутины. Ошибка загрузки удаляет tmp; сверка хеша предотвращает установку неполного файла. Выбор победителя одновременных правок относится к folder и за пределами этого сетевого ревью; сетевые ошибки возвращаются в повторную сверку runPeer, кроме зависания из 01-01-05.
- Unit использует DynamicUser, NoNewPrivileges, пустой capability set, строгую защиту ФС, namespace/syscall restrictions и UMask=0077. Подтверждённого обхода этой песочницы не найдено; на macOS unit не запускался.
