# 01-02 — ревью ядра синхронизации

Область: `internal/folder/*`, `internal/app/daemon.go`, `internal/app/activity.go`, `internal/config/config.go`; transport прочитан для проверки вызывающего пути. Исходники не изменялись. Доказательства ниже — конкретные пути исполнения, без временных репро-тестов.

### 01-02-01 [critical] Симлинки позволяют писать и удалять вне синхронизируемой папки
- Где: internal/folder/apply.go:24, :204, :205, :212, :217, :224, :234, :270.
- Сценарий: в корне есть `link -> /внешний/каталог`; сопряжённый пир присылает новый `link/new.txt`. Файл создаётся вне корня. Для ранее индексированного `dir/file` локальная замена `dir` на симлинк также позволяет удалить внешний файл, если размер и mtime совпали с индексом.
- Доказательство: validName проверяет только синтаксис строки; `link/new.txt` проходит. При отсутствии внешнего new.txt `diskMatches(target,nil)` возвращает true; MkdirAll следует существующему link, Rename переносит загруженный файл наружу. Stat следует ссылкам. Между Stat и Rename/Remove нет защиты от замены родителя: scanMu блокирует лишь собственные операции демона, а не локальный процесс. Проверка через EvalSymlinks сама по себе эту гонку не исправит.
- Исправление: операции относительно удерживаемого дескриптора корня с запретом выхода через ссылки, включая создание родителей, rename, unlink, чтение и удаление пустых каталогов; использовать доступные платформенные средства безопасного обхода. Затрагивает apply.go и чтение файлов через Lookup/transport.
- Уровень исправления: L3.

### 01-02-02 [high] Недоступный подкаталог превращается в удаление его содержимого
- Где: internal/folder/scan.go:92–119, :163–171; internal/folder/apply.go:50–55, :216–220.
- Сценарий: после успешной синхронизации ReadDir подкаталога временно возвращает EACCES/EIO либо Info файла возвращает ошибку. Следующий скан публикует tombstone для существующих файлов; пир без собственных изменений удаляет свои копии.
- Доказательство: ошибка не в корне логируется и заменяется на nil (93–99), ошибка Info также теряется (115–117). Потомки не попадают в seen; цикл 164–170 увеличивает локальный вектор и записывает Deleted. На пире этот вектор Greater, decide возвращает take и выполняется Remove. Ошибка hashFile отличается: seen уже выставлен, поэтому сама по себе она удаления не создаёт.
- Исправление: не публиковать удаления при неполном обходе; учитывать недоступные поддеревья либо коммитить снимок только после полностью успешного обхода. scan.go.
- Уровень исправления: L2.

### 01-02-03 [high] Потеря точки монтирования или смена пути запускают массовое удаление
- Где: internal/folder/index.go:155–159, :170–182; internal/folder/scan.go:100–102, :163–171; internal/config/config.go:94; internal/app/daemon.go:161–169.
- Сценарий: диск отмонтирован, на его месте остаётся пустой каталог; либо config.Folder изменён на новый пустой путь при сохранённом index.json. Все ранее известные файлы удаляются у пира. Корень-симлинк ещё опаснее: WalkDir не обходит его, а callback принимает сам корень без проверки типа.
- Доказательство: Open создаёт отсутствующий корень и загружает прежний индекс без привязки к идентичности каталога. Scan пустого существующего корня успешен, seen пуст, все записи получают Deleted с большей версией. При корне-симлинке callback на строке 100 возвращает nil, обход потомков не происходит. Ошибка доступа непосредственно к обычному корню, напротив, возвращается и удаления не коммитятся.
- Исправление: связать индекс с подтверждённым корнем/идентичностью тома; не создавать исчезнувший рабочий корень автоматически при существующем индексе; проверять тип и доступность корня, явно переинициализировать индекс при смене папки. index.go, scan.go, config.go/daemon.go.
- Уровень исправления: L3.

### 01-02-04 [high] Устаревший план применения затирает конкурентную версию без конфликта
- Где: internal/folder/apply.go:113–127, :188–205, :257–258, :269–277; internal/app/daemon.go:342, :500.
- Сценарий: два runPeer одновременно планируют разные входящие версии одного файла относительно старой записи L. Оба входящих файла имеют размер и mtime как у L, но другое содержимое. Первый устанавливает R1, второй после загрузки устанавливает R2 по старому решению take, уничтожая R1 без conflict-копии. Аналогично локальная запись после проверки Stat, но до Rename/Remove, теряется.
- Доказательство: план снимался до download и scanMu. Под scanMu повторно не сравнивается текущий индекс/вектор; diskMatches сравнивает только размер и mtime. После применения R1 с теми же метаданными проверка второго проходит, несмотря на другой хеш и версию. В отличие от mergeOnly обычный путь не проверяет cur.Version. Локальный процесс вообще не участвует в scanMu; изменение между 205 и 234 перезаписывается.
- Исправление: повторно вычислять решение по текущему индексу под блокировкой после загрузки, проверять содержимое/идентичность локального файла; для несогласованных внешних писателей обеспечить сохранение заменяемой версии и повторную проверку. apply.go.
- Уровень исправления: L3.

### 01-02-05 [high] Конкурентные сохранения повреждают index.json и гоняются с mergeOnly
- Где: internal/folder/index.go:203–219; internal/folder/apply.go:100–106, :183; internal/folder/scan.go:182; internal/app/daemon.go:342, :500.
- Сценарий: два пира заканчивают ApplyRemote одновременно либо его отложенный save пересекается со Scan. Параллельные WriteFile используют один `index.json.tmp`: один writer может усечь файл, который другой уже переименовал в index.json, либо смешать JSON. Рестарт затем не может открыть индекс. Возможен и откат к более старому снимку с утратой tombstone.
- Доказательство: save удерживает mu лишь при сборе указателей, затем освобождает его до Marshal и I/O. ApplyRemote вызывает save уже после выхода из applyOne и освобождения scanMu; несколько runPeer независимы. Все save пишут один tmp без сериализации. Кроме того, mergeOnly меняет поле Version того же FileInfo по указателю, пока save маршалит этот объект без mu: это data race. Open возвращает ошибку при повреждённом JSON (index.go:175–177).
- Исправление: отдельная сериализация сохранений, глубокий неизменяемый снимок под mu, уникальные временные файлы и порядок публикации снимков; не терять ошибки сохранения. index.go, apply.go.
- Уровень исправления: L3.

### 01-02-06 [high] Имя conflict-файла допускает уничтожение предыдущей сохранённой версии
- Где: internal/folder/apply.go:210–215, :300–304; internal/folder/scan.go:134–155.
- Сценарий: рядом уже существует рассчитанный conflict-файл, например сохранённая ранее версия того же имени с mtime в ту же секунду. Новый конфликт заменяет его локальной проигравшей версией, уничтожая старое содержимое.
- Доказательство: имя зависит от имени оригинала, секунд mtime и фиксированного ID; наносекунды/хеш/уникальный номер отсутствуют. os.Rename на macOS/Linux заменяет существующий обычный файл без ошибки. Никакой проверки или резервирования имени нет. Conflict-файлы не входят в builtinIgnore и затем сканируются/синхронизируются как обычные; столкновение их версий может породить дополнительные conflict-файлы.
- Исправление: уникальное резервирование имени без замены существующего файла, стабильный идентификатор версии/хеш; определить поведение синхронизации сохранённых конфликтов. apply.go, при необходимости scan.go.
- Уровень исправления: L2.

### 01-02-07 [high] NFC-коллизии на Linux скрывают файл и позволяют удалить другую локальную копию
- Где: internal/folder/scan.go:103–105, :119–126, :141–155; internal/folder/apply.go:200–217; internal/folder/index.go:259–266.
- Сценарий: Linux хранит одновременно `é.txt` (NFC) и `é.txt` (NFD). Оба получают один ключ индекса. Если размер/mtime равны, второй пропускается даже при другом содержимом; один файл никогда не уходит пиру. Если метаданные различны, запись и Disk последнего файла заменяют первую, и входящее удаление общего имени удаляет именно выбранную копию.
- Доказательство: name без проверки коллизий нормализуется NFC, seen и files используют только name. Unchanged не сравнивает disk или хеш. Индекс способен представить ровно один из двух реально существующих файлов; ApplyRemote использует его Disk. Входящие имена также не проверяются на NFC: NFD-ключ, присланный пиром, после Scan становится другим ключом с tombstone для исходного имени.
- Исправление: обнаруживать коллизии до публикации скана и сохранять обе версии под безопасными именами либо останавливать проблемные записи; требовать канонические входящие имена. scan.go, apply.go, index.go.
- Уровень исправления: L2.

### 01-02-08 [high] Файлы и индекс подтверждаются без обеспечения долговечности на диске
- Где: internal/folder/apply.go:234–258, :280–297, :100–106; internal/folder/index.go:215–219.
- Сценарий: после успешно применённого обновления происходит сбой питания. Новый индекс с версией R может оказаться сохранён, а байты файла/rename — нет. После рестарта Scan воспринимает старый/пустой файл как новое локальное изменение поверх R, либо отсутствие как удаление, и распространяет повреждение обратно.
- Доказательство: download делает Close, но не Sync; отсутствуют fsync файла после chmod/mtime и fsync каталога после rename/delete. save также ограничен WriteFile+Rename без Sync и без согласованного порядка долговечной фиксации с данными. Присутствующий атомарный rename защищает видимость при штатной работе, но не гарантирует сохранность при сбое питания. Ошибка save лишь логируется при уже успешном ApplyRemote.
- Исправление: определить crash-consistent порядок фиксации данных, каталогов и индекса, делать Sync и обрабатывать его ошибки; при необходимости журналировать операции и восстанавливать их до обычного скана. apply.go, index.go, scan.go.
- Уровень исправления: L3.

### 01-02-09 [medium] Применение обновления расширяет доступ к приватному файлу
- Где: internal/folder/apply.go:227–234; internal/folder/scan.go:138; internal/folder/index.go:80–88.
- Сценарий: синхронизируемый файл локально имеет 0600 или скрипт 0700. Обновление содержимого с пира заменяет inode файлом 0644/0755: другие пользователи с доступом к каталогу получают чтение секретов.
- Доказательство: исходные права не сохраняются, передаётся только Exec. Chmod временного файла явно выставляет 0644/0755, независимо от umask и прав прежнего inode, затем выполняется Rename.
- Исправление: сохранять локальные ограничения доступа существующего файла и выбрать безопасную политику для новых; согласовать переносимые атрибуты. apply.go, при необходимости FileInfo/scan.go.
- Уровень исправления: L2.

### 01-02-10 [medium] Изменения исполняемого бита не распространяются
- Где: internal/folder/scan.go:123–126, :138, :145–146; internal/folder/apply.go:49–53, :223–231.
- Сценарий: пользователь делает chmod +x скрипту без изменения содержимого. Пир продолжает хранить неисполняемый файл; при входящем metadata-only обновлении Greater с тем же хешем chmod также не выполняется.
- Доказательство: unchanged учитывает size/mtime, но не mode (chmod обычно меняет ctime). Даже если пересканировать по другой причине и попасть в hash-путь, одинаковый хеш сохраняет прежний вектор. Equal удалённой версии пропускается. Chmod находится внутри `tmp != ""`, а download не нужен при равном хеше.
- Исправление: включить Exec в определение локального изменения и вектор версии; применять атрибуты даже без скачивания. scan.go, apply.go.
- Уровень исправления: L2.

### 01-02-11 [medium] Сопряжённый пир может заполнить диск незавершённой загрузкой
- Где: internal/folder/apply.go:280–295; internal/transport/transport.go:225–234; internal/app/daemon.go:500.
- Сценарий: пир объявляет маленький файл, затем бесконечно отдаёт тело с медленным прогрессом. Демон пишет его в корень синхронизации до заполнения диска, загрузка данного пира не завершается, обычные записи других программ начинают ошибаться.
- Доказательство: r.Size используется для прогресса, но не ограничивает writer; Fetcher вызывает неограниченный io.Copy. Проверка хеша и очистка происходят лишь после завершения fetch. Для Fetcher нет собственного deadline (в отличие от Index); контекст живёт до паузы/остановки. Для больших корректных файлов память расходуется потоково, но квоты диска нет.
- Исправление: проверять неотрицательный размер и ограничивать поток объявленным размером с обнаружением лишнего байта, установить лимиты/таймаут отсутствия прогресса и бюджет одновременных загрузок. apply.go и вызывающий контракт transport.
- Уровень исправления: L2.

### 01-02-12 [medium] Журнал активности маршалит общие Day вне мьютекса
- Где: internal/app/activity.go:65–73, :115–119; internal/app/daemon.go:224–225, :257–258, :365.
- Сценарий: watchLoop сохраняет статистику, пока обработчик отдачи файла или runPeer добавляет событие за тот же день. Чтение счётчиков Marshal и запись add выполняются конкурентно; сохраняется несогласованная статистика, race detector может завершить процесс теста с ошибкой.
- Доказательство: flush копирует указатели *Day в f.Days под mu, затем снимает mu до json.Marshal. add под mu изменяет поля тех же объектов. Этот мьютекс уже не защищает чтение Marshal. dirty также сбрасывается до I/O: ошибка записи/rename теряет необходимость повторить flush, если новых событий не будет.
- Исправление: копировать значения Day под mu и сохранять неизменяемый снимок; при ошибке сохранять dirty с учётом поколений событий. activity.go.
- Уровень исправления: L1.

## Покрытие остальных сценариев

- Абсолютные пути, `../`, внутренние `..`, обратный слеш и NUL отклоняются validName. Точка `.` допускается, но обычное применение упирается в существующий корень и diskMatches; отдельный подтверждённый выход через неё не найден. Длинные/недопустимые для ФС имена приводят к ошибке операции, однако нормализация и коллизии не проверяются.
- Коллизия регистра на APFS известна README: при получении одновременно A.txt/a.txt второй путь обнаруживается как существующий при l=nil, возвращается errLocalChanged, сохраняется постоянный retry. Автоматического разрешения/представления двух файлов нет; отдельной доказанной перезаписи из этого сценария не заявляем.
- При штатном обрыве fetch до EOF или несовпадении SHA-256 временный файл удаляется до замены оригинала. Rename выполняется после полной проверки хеша. Сбой процесса оставляет игнорируемый `.sharedir-tmp-*`; очистки таких остатков при старте нет.
- Векторы отличают последовательные изменения от параллельных. Для параллельных edit/delete код намеренно отдаёт приоритет edit независимо от времени, то есть удалённый файл может воскреснуть; это фактическая политика, которую следует описать отдельно от общего правила README. Для edit/edit используются часы ФС и tie-break по ID, поэтому при расхождении часов физически более поздняя правка может проиграть, но должна сохраняться conflict-копия (с оговоркой 01-02-06). Само расхождение часов не объявляем потерей байтов.
- scanMu сериализует штатный watcher/Scan с установкой файла и индекса, поэтому собственная успешная запись с зафиксированным реальным mtime не должна порождать обратную локальную правку. Планирование до блокировки и сохранение после её освобождения дают исключения 01-02-04/05.
- Повторное подключение сбрасывает since; неудачные применения повторяются через пять секунд. Отмена runPeer при паузе не ожидает завершения старого runPeer перед запуском нового при resume; старое применение, уже прошедшее download, не проверяет ctx под scanMu. Это расширяет окно 01-02-04/05. Relay watcher завершается через done/отмену poll; явного отдельного дедлока в изученных блокировках не найдено.

## Под вопросом

1. runPeer читает pr.st.Name без pr.mu в daemon.go:482, тогда как Pair/syncPeers обновляет имя под блокировкой. Есть путь для гонки при одновременной потере связи и переименовании пира; значимых последствий для данных сверх неверного имени в логе не установлено.
2. Входящий вектор может содержать максимальный uint64: tick переполнится. Проверки диапазона/допустимых ID нет; длительное влияние на сходимость требует отдельного репро протокола.
