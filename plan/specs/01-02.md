# 01-02 Ревью: ядро синхронизации

## Target
Проект sharedir: двусторонняя синхронизация одной папки между macOS и Linux. Go-демон (`cmd/sharedir`, `internal/*`). Обнаружение — UDP-броадкаст в LAN (порт 22101), передача — взаимный TLS 1.3 на 22100, ID устройства = SHA-256 сертификата, подключаться может только явно сопряжённое устройство. Есть relay через свой VPS для связи через интернет. Конфликты: побеждает более поздняя правка, другая сохраняется как `имя.sync-conflict-ДАТА-ВРЕМЯ-УСТРОЙСТВО.ext`. Подробности — `README.md`.

Область ревью (только чтение): `internal/folder/` (apply.go, index.go, scan.go, watch_darwin.go, watch_linux.go), `internal/app/daemon.go`, `internal/app/activity.go`, `internal/config/config.go`. Сетевую часть (`internal/transport`, `internal/relay`) читай только чтобы понять вызовы.

## Change
Найди баги, ведущие к потере или порче данных, и уязвимости при применении изменений от пира. Обязательно проверь:
- Пути от пира: `..`, абсолютные пути, симлинки (в том числе симлинк внутри папки, указывающий наружу, и гонка «проверили путь — подменили на симлинк»), регистр имён на macOS (APFS без учёта регистра) против Linux, Unicode-нормализация NFC/NFD, недопустимые имена.
- Применение файла: запись во временный файл + атомарный rename, fsync, проверка хеша до замены, частично принятый файл при обрыве, права файлов, большие файлы.
- Конфликты: правило «побеждает поздняя правка» при расхождении часов, одновременная правка на двух машинах, удаление против правки, возрождение удалённых файлов, генерация имени conflict-файла (коллизии, синхронизация самих conflict-файлов по кругу).
- Индекс и скан: гонки между watcher, сканом и применением входящих изменений (собственная запись не должна считаться локальной правкой и уходить обратно), согласованность индекса после краша, временная ошибка чтения не должна превращаться в удаление на пире.
- Удаления: может ли пустая или недоступная папка (отмонтированный диск, неверный путь в конфиге) привести к массовому удалению у пира.
- Конкурентность в daemon.go: общие map/срезы без мьютекса, дедлоки, утечки горутин.

## Constraints
- Это ревью: **исходный код не меняй**. Единственный файл, который ты создаёшь и коммитишь, — `plan/reviews/01-02.md`.
- Чтобы подтвердить находку, можно писать временные тесты и запускать их (`go test -race -run … ./internal/…`), но перед коммитом удали их. Код репро-теста вставь в отчёт.
- Включай только то, что подтверждено кодом (конкретный путь исполнения) или запуском. Догадки без пути исполнения — в отдельный раздел «Под вопросом», не больше 5 пунктов.
- Стиль и вкусовщину не пиши. Нужны баги, гонки, потеря данных, уязвимости, неверная обработка ошибок с реальными последствиями.
- Проверь все конкурирующие пути: горутины, повторные подключения, одновременные правки на двух машинах, обрыв посреди передачи, рестарт демона.
- Отчёт — на русском языке.

## Формат отчёта `plan/reviews/01-02.md`
Находки отсортированы по серьёзности. Каждая — отдельный раздел:

```
### 01-02-NN [critical|high|medium|low] Короткое название
- Где: path/to/file.go:LINE (и другие места)
- Сценарий: входные данные / состояние → что происходит не так (конкретно)
- Доказательство: путь исполнения по строкам или репро-тест (код + вывод)
- Исправление: что поменять, какие файлы задеты
- Уровень исправления: L1|L2|L3 (L1 — локально, решение очевидно; L2 — логика в 1–2 модулях; L3 — несколько модулей, конкурентность, протокол)
```

В конце — таблица «ID | серьёзность | файл | уровень» и раздел «Под вопросом».

## Observable acceptance
```
test -s plan/reviews/01-02.md
git diff --stat main -- . ':!plan'        # пусто: исходники не тронуты
go vet ./... && go test -race ./... 2>&1 | tail -20   # зелёный, как и до ревью
```
Закоммить отчёт одним коммитом `review: 01-02`. Ненулевой выход команд приёмки = задача провалена.

## Ownership
Создаёшь только `plan/reviews/01-02.md`. Остальное — только чтение.
