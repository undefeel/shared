Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.

## Change
Implement rows 04-33…04-39 of the table «Задачи реализации» in `plan/design/perf.md`, sections R6, R7, R8, R9, R10, R18 (plus the matching rows of «Конкурирующие пути»). One vertical slice of the folder scan/watch subsystem:
- **R6 own events (04-33):** the group coordinator registers expected fingerprints after G4; exact own events do not trigger a Scan; ambiguous/mixed events stay dirty; an external write with the same name/mtime is never lost; the root event is never suppressed.
- **R7 watcher paths (04-34) + incremental Scan (04-37):** watch API returns batches of relative paths + FullRequired/RootChanged + generation; FSEvents dropped/MustScanSubDirs, inotify overflow, addTree error, stream close → full Scan; rename marks both parents; unknown old name or ignore-file change → full walk; canonical collisions checked against the whole map; scope errors cancel the whole candidate without deletes; last counted file deletion requires a confirming full walk (root latch).
- **R8 stability (04-35):** N=1 s, two equal size+mtime+inode+Exec probes then stableHash with fstat before/after; pending map bounded 10000 (overflow → full rescan needed); no sleeping under a mutex; endless writer is deferred and visible as pending; incoming files do not wait.
- **R10 Scan staging/lease (04-36):** snapshot baseline/generation/ignore revision and a rootFS lease under a short lock; walk and hash without scanMu/mu; close/rebind waits for leases outside the commit lock; on return re-check guardRoot, generation, baseline revision, stat of candidates and parents; a concurrent commit/rebind cancels the whole candidate and retries.
- **R9 schedule (04-38):** full Scan at start after recovery, every 12 min with a healthy watcher, every 60 s without/with a failed watcher, overflow immediately; an event storm cannot starve the timer; one full scan at a time, later signals coalesce keeping dirty scopes; full Scan forces hash even with equal stat.
- **R18 built-in excludes (04-39):** owner decision: `node_modules`, `.venv`, `__pycache__`, `.next`, `dist` (by path component, not substring), temp names `.sharedir-tmp-*`, `*.swp`, `*.swo`, `*~`, `.#*`, `#*#`, `~$*`, `*.crdownload`, `*.part`, `*.download`; `.git` stays INCLUDED. Same rules for watcher, Scan and Apply; built-ins take priority, the user ignore file adds restrictions; already indexed files that become excluded are kept as ignored records (never tombstoned, not offered in the active exchange).
Tests: the scenarios listed in each row of the table (column «тесты») plus the harness scenario: after the initial sync of 2092 files, a burst of own incoming writes triggers no full Scan, and one external edit is picked up by the incremental path.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O, directory walks or hashing under scanMu/mu (the post-capture hash inside the commit stays under the lock by design).
- A transient error (ReadDir/stat/hash/watch failure) never turns into a delete, a tombstone or data loss; a durability error never means success.
- Keep every stage 02/04 guarantee: rooted fd / no-follow, NFC, no-replace, capture, recovery before Scan/watcher/network, durable empty/changed-root latch.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-70.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-70 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 04-70 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-70` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-70 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.
