# 04-73 Wave B1b: Scan staging without scanMu and incremental Scan

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.

## Change
Part 2 of 3 of wave B1 (rows 04-36 and 04-37 of «Задачи реализации» in `plan/design/perf.md`, sections R10 and R7; builds on 04-72 stability/ignore).
- **R10 Scan staging/lease:** under a short lock snapshot baseline/generation/ignore revision and take a rootFS lease; the walk and hashing run without scanMu/mu (04-70 review blocker: scan.go walks/hashes under scanMu); close/rebind waits for leases outside the commit lock (no deadlock); on return take scanMu → saveMu and re-check guardRoot, generation, baseline revision, stat of every candidate and parent, absence of entries to delete; a concurrent commit/rebind cancels the whole candidate and schedules a retry; events since the walk start stay pending.
- **R7 incremental Scan API:** `ScanPaths(ctx, scopes)` (name it as you see fit) taking relative dirty paths: rename marks both parents; a directory scope rescans the subtree; unknown old name or ignore-file change → full walk; canonical collisions checked against the whole map, not only the scope; ReadDir/stat/hash error cancels the whole candidate without deletes; deletion of the last counted file requires a confirming full walk (root empty latch). Plus an in-memory stat/hash cache (`scan_cache.go`) used by the event path; a full Scan forces hashing even with equal stat.
Tests: the row scenarios (no scanMu during hash — prove with a concurrent commit that completes while a slow hash is in progress; rebind waits for lease; rename/delete scope; collision with an outside-scope name; last-file root latch; error → no deletes) and an incremental scan of 1 changed file among 2092 that does not hash the others.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O, directory walks or hashing under scanMu/mu (the post-capture hash inside the commit stays under the lock by design).
- A transient error (ReadDir/stat/hash/watch failure) never turns into a delete, a tombstone or data loss; a durability error never means success.
- Keep every stage 02/04 guarantee: rooted fd / no-follow, NFC, no-replace, capture, recovery before Scan/watcher/network, durable empty/changed-root latch.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-73.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-73 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 04-73 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-73` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-73 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.

Extra rules for this task (learned on 04-60…04-71: luna repeatedly gave up on whole plans):
- Give the implementer small pieces: parts or sequential phases of at most ~300 lines each, every piece naming exact files, functions, signatures and tests. Prefer 2–3 pieces over one big `implement`.
- Takeover is mandatory and complete: after the fix rounds you finish everything that is missing yourself. Sending worker_done with outcome failed is acceptable only for a concrete technical blocker you name; "not finished" is not a blocker.
