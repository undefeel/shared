# 04-60 Parallel downloads and daemon pipeline (merged 04-24 + 04-32)

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.

## Change
Implement rows 04-24 (download pool) and 04-32 (daemon pipeline) of the table «Задачи реализации» in `plan/design/perf.md` as one vertical slice; read sections R1 (backpressure), R11, R13, R15, «Конкурирующие пути», and the owner decisions.
- Download pool: up to `download_concurrency` (config, 04-23, default 6) parallel downloads shared across all peers, bounded staging, cancel closes response bodies; downloaded files are handed to the group coordinator (04-20/04-22) so ready files commit in groups.
- Daemon pipeline in `internal/app/daemon.go`: use the v2 client (04-30: /hello, named index refresh, /files batches from 04-29 for small files, single-file gzip over relay), the retry queue from 04-31 (`internal/app/peer_queue.go`) so one failed file never resets the cursor or re-fetches the full index, and wire the real transport StateProvider/HelloProvider from folder (store epoch/cursor from the 04-17 store; peer-set epoch is a placeholder until wave C).
- An incompatible peer (no v2 /hello, version mismatch) sets a clear peer state in `Status` (e.g. state "incompatible" plus a short reason) instead of a silent retry loop; document the exact JSON field names in a comment, the UI task 04-61 will consume them.
- Pause/unpair/rebind drain the pipeline and pool before the old generation is released.
Required tests: two peers share the concurrency limit; cancel closes bodies; bounded staging; cursor unchanged when one body fails and only that file is retried; batches and pool are actually used; pause drains; incompatible peer appears in Status.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).

- A transient error never turns into a delete, a tombstone or data loss; a durability error never means success.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-60.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-60 implement`. A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-60` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-60 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
6. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.
