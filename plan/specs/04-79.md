# 04-79 Profile and fix the first-sync slowdown of wave B

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.


## Change
After wave B (tasks 04-71…04-74) the perf harness `SHAREDIR_PERF=1 go test -run Perf -count=1 ./internal/app/` got ~30% slower: median ~2.2 s before 04-72 → ~2.87 s now for 2092 files (fsync 2648, FULLFSYNC 99, G=33 unchanged, so it is CPU/lock/wait time, not durability). Test suite time also grew (folder ~110 → ~148 s, app ~76 → ~88 s). Stage notes at the bottom of `plan/04-perf.md` list which task changed what.
1. Measure: CPU, block and mutex profiles of the harness (`-cpuprofile`, `-blockprofile`, `-mutexprofile` on `go test`); if useful, bisect over the merge commits of 04-71…04-74 (`git log --merges --oneline -8`) running the harness at each. Identify the main causes with numbers.
2. Fix the causes that do not weaken any guarantee (e.g. redundant stat/hash, stability probes or waits on the initial sync path, extra copies, lock contention, needless sleeps/timers in tests). Do not remove features of wave B; do not weaken stability, exclusion, reuse or own-event semantics.
3. If test time growth comes from sleeps/timeouts in tests, shorten them via injectable clocks/intervals where cheap.
Goal: median back to ≤ ~2.3 s, or a clear numeric explanation of what remains and why it is required.

Write findings (profile tables, bisect numbers, what you changed, before/after) to `plan/specs/04-79.review.md`.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O, directory walks or hashing under scanMu/mu.
- A transient error (network, ReadDir/stat/hash, peer offline) never turns into a delete, a tombstone, a GC or data loss; a durability error never means success.
- Keep every stage 02/04 guarantee: rooted fd / no-follow, NFC, no-replace, capture, recovery before Scan/watcher/network, durable empty/changed-root latch, group commit with one F_FULLFSYNC per device per phase, protocol v2 only.
- List in the commit messages the competing paths you checked («Конкурирующие пути» in perf.md).
- If you change a number or a rule, grep `README.md`, `docs/`, `plan/design/perf.md` and report mismatches in worker_done (docs are task 04-78).
- The harness (`SHAREDIR_PERF=1 go test -run Perf ./internal/app/`) must stay green; report its numbers before/after in worker_done. The current median is ~2.87 s for 2092 files; do not make it slower.
- Communicate in English.
- Budget: up to ~600 lines of code changes. You may do it yourself or delegate pieces via the lead workflow below.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-79.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-79 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 04-79 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A terra worker (default implementer) implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-79` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-79 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.

Extra rules (learned on 04-70…04-74):
- The default implementer is terra (gpt-6.1-terra): on 04-73 it carried ~1100 lines in 3 pieces without takeover. Give it pieces of up to ~600 lines each (sequential phases or disjoint parts), each naming exact files, functions, signatures and tests. Use `LEAD_IMPL=luna` only for tiny pieces (~300 lines); do not pick luna for whole parts.
- If the implementer ends its turn without reporting, `lead.sh` continues it automatically; just keep waiting.
- Takeover is mandatory and complete: after the fix rounds you finish everything that is missing yourself. worker_done with outcome failed is acceptable only for a concrete technical blocker you name.
