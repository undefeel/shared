## Change
Implement row 04-54 of the table «Задачи реализации» in `plan/design/perf.md`, section «Пороги приёмки R20», with thresholds recomputed by owner decision item 1 (one F_FULLFSYNC per device per group phase).
- Two real in-process app.Daemon with mTLS HTTP/2 loopback, temp state/root, 2092 deterministic unique files of 11 KiB, depth up to 4, concurrency 6; real flush counters through the per-Folder PersistenceProbe (04-15: SetPersistenceProbe before concurrent use, PersistenceStats). No mocked fsync for the main numbers.
- Assert: index bytes written by the receiver ≤ 4 MiB; repeated no-op Scan writes 0 bytes and 0 flushes; bytes(4000) ≤ 2.3 × bytes(2000) + 256 KiB (no O(N²)); FULLFSYNC count ≤ 3G + 12 with G = number of groups; average group size ≥ 32 with a ready queue.
- Time: run as a test with a generous timeout plus a `go test -bench` or `-run` mode that prints files/s, bytes written and flush counts; put the time threshold (median ≤ 30 s) behind an env flag (e.g. SHAREDIR_PERF=1) so normal CI is not flaky; the byte/flush/O(N) assertions run always.
- In worker_done report the measured numbers from this machine (files/s, total time, index bytes, flush counts, G).

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-62.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-62 implement`. A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-62` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-62 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.
