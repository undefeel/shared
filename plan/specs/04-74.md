# 04-74 Wave B1c: watcher batches, own-event suppression and scan schedule

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.

## Change
Part 3 of 3 of wave B1 (rows 04-33, 04-34 and 04-38 of «Задачи реализации» in `plan/design/perf.md`, sections R6, R7 (watcher side) and R9; builds on 04-72 and 04-73: use the incremental Scan API and stability from them).
- **Watcher paths:** `watch_darwin.go` / `watch_linux.go` emit batches of relative paths + FullRequired/RootChanged + generation; FSEvents dropped/MustScanSubDirs/history loss, inotify overflow, addTree error, stream close → full Scan; a new directory tree installs watches first and then checks its content; built-in/user excludes filtered (use the 04-72 ignore API).
- **R6 own events:** the group coordinator registers expected fingerprints (generation, dev/inode, size, mtime, Exec, hash) after G4 (`group.go`); exact own events do not trigger a Scan; ambiguous/mixed events stay dirty and go through the incremental hash check; an external write with the same name and mtime is never lost; the root event is never suppressed; matching is never by time alone.
- **R9 schedule:** `internal/app/scan_schedule.go` wired in `daemon.go`: full Scan at start after recovery, every 12 min with a healthy watcher, every 60 s with no/failed watcher, overflow immediately; an event storm cannot starve the timer; one full scan at a time, later signals coalesce keeping dirty scopes; dirty batches go to the incremental Scan.
Tests: row scenarios (exact self event suppressed, external same-mtime edit preserved, root event never suppressed; dropped/overflow → full, rename parents, addTree error, root changed; 12 min/60 s with a fake clock, overflow immediate, storm no starvation) and a harness scenario in `internal/app/perf_integration_test.go`: after the initial 2092-file sync a burst of own incoming writes triggers no full Scan, and one external edit on the receiver propagates through the incremental path.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O, directory walks or hashing under scanMu/mu (the post-capture hash inside the commit stays under the lock by design).
- A transient error (ReadDir/stat/hash/watch failure) never turns into a delete, a tombstone or data loss; a durability error never means success.
- Keep every stage 02/04 guarantee: rooted fd / no-follow, NFC, no-replace, capture, recovery before Scan/watcher/network, durable empty/changed-root latch.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-74.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-74 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 04-74 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-74` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-74 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.

Extra rules for this task (learned on 04-60…04-71: luna repeatedly gave up on whole plans):
- Give the implementer small pieces: parts or sequential phases of at most ~300 lines each, every piece naming exact files, functions, signatures and tests. Prefer 2–3 pieces over one big `implement`.
- Takeover is mandatory and complete: after the fix rounds you finish everything that is missing yourself. Sending worker_done with outcome failed is acceptable only for a concrete technical blocker you name; "not finished" is not a blocker.
