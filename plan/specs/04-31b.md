# 04-31b Retry queue — oversized index continuation (review fix)

## Target
Project sharedir (Go daemon). An independent review found a defect that is still present. Keep the existing commits, add new ones.

## Change
1. [major] `peer_queue.go` ~54-58, 99-109: for an index larger than `peerPendingLimit`, accept stores only a prefix and leaves the cursor unchanged; after any prefix item applies, `canPoll` permits another poll, and replaying the same full index re-adds the already applied prefix (and with reset=true first deletes the remaining pending prefix). The queue can starve the suffix or lose pending work indefinitely. Fix: keep per-index continuation state (e.g. the index identity/cursor being consumed plus the position or set of names already accepted/applied) so that replaying the same index skips already accepted or applied entries and continues with the suffix; reset only on a genuinely new index (new cursor/epoch). The cursor advances only after every record of that index has been accepted and applied (or superseded by a newer Vector).
2. [minor] `peer_queue_test.go` ~92-102: replace the overflow test with one that resends the unchanged oversized index through several capacity-release cycles and asserts every record is queued and applied exactly once before the cursor advances, with no record lost and no applied record re-queued. Also cover reset=true on the same index (must not drop pending suffix) and a newer Vector for a record arriving mid-continuation.
Keep all existing behaviour and tests from rounds 1-2 (no deadlock on overflow or drain, cross-peer unblock, duplicate-name newest Vector).
