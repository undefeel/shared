# 05-01 Clean up and speed up internal/folder tests

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app, Omarchy widget. Core guarantees: `plan/design/folder.md`, `plan/design/perf.md`. Test policy: `plan/TESTING.md` (read it first; its risk list defines which scenarios must keep a test).

Stage 05 (owner decision 2026-11-05): tests consume too much worker time and model limits. Reduce the NUMBER of tests and the TIME of the test suite, without losing protection of the risk-list scenarios. This is a test-only cleanup.

## Change
Package `internal/folder`: 7803 test lines, `go test -count=1 ./internal/folder/` takes ~119 s (no -race). Slowest: TestSyncLifecycle 10.4 s, TestGroupCrashMatrix 9.0 s, TestDeltaStaging 8.7 s, TestReuseApplyAndChangedDonor 4.3 s, TestTwoPeersConcurrentEditDeleteIntegration 4.2 s, TestIgnoredRecordsSurviveRestartAndRestore 3.1 s. 13 tests take exactly ~2.1 s each (TestCrashAfter*Integration, TestStoreConfirmEpochAndHistory, TestExecTrueMetadataOnlyDoesNotFetch, …) — likely a fixed ~2 s wait (stability window, settle or flush); find the cause and remove it from tests via a lowered test interval or condition polling.
1. Measure: per-test time (`go test -count=1 -json ./internal/folder/ | jq ...`), coverage, find duplicates.
2. Write the cleanup plan (which tests go, merge, shrink, speed up) to `plan/specs/05-01.plan.md`, then implement it.

## Constraints
- Production behaviour must not change. Allowed production edits: only small test hooks for timing (an unexported variable or option for an interval/timeout/stability window that tests can lower), with defaults byte-for-byte the same. No other production changes; if you think one is needed, report it in worker_done instead.
- Every scenario of the risk list in `plan/TESTING.md` (data survives interruption between steps; a transient error never becomes a delete/tombstone; competing paths under -race; malformed/incompatible messages rejected without panic) keeps at least one test in your packages. Before deleting a test, check whether it is the only one covering such a scenario.
- Statement coverage (`go test -cover`) of each owned package may drop by at most 2 percentage points. Measure before and after, report both.
- Ways to cut: delete duplicates and tests that only re-check what another test already covers; merge near-identical tests into table tests; shrink fixtures (fewer files, smaller sizes) while keeping the scenario; replace fixed sleeps/waits with condition polling or lowered test intervals; remove assertions of private internals that a behaviour test already covers.
- Do not raise timeouts, do not add t.Skip (except the perf gating explicitly asked for below), do not weaken assertions of the surviving tests.
- Tests must stay deterministic and pass under -race; run the full suite at least twice at the end to catch flakiness.
- No new dependencies. Communicate in English.
- Report in worker_done: before/after package time (`go test -count=1 ./internal/<pkg>/`, no -race), before/after test line count (`wc -l`), before/after coverage, list of deleted/merged tests with one-line reasons, and any risk-list scenario you consciously left with a single test.

Any non-zero exit code = task failed. Targets: `internal/folder` ≤ 60 s without -race, test lines −30% or more, coverage drop ≤ 2 pp.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/05-01.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 05-01 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 05-01 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A terra worker (default implementer) implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 05-01` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 05-01 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.

Extra rules (learned on 04-70…04-74):
- The default implementer is terra (gpt-6.1-terra): on 04-73 it carried ~1100 lines in 3 pieces without takeover. Give it pieces of up to ~600 lines each (sequential phases or disjoint parts), each naming exact files, functions, signatures and tests. Use `LEAD_IMPL=luna` only for tiny pieces (~300 lines); do not pick luna for whole parts.
- If the implementer ends its turn without reporting, `lead.sh` continues it automatically; just keep waiting.
- Takeover is mandatory and complete: after the fix rounds you finish everything that is missing yourself. worker_done with outcome failed is acceptable only for a concrete technical blocker you name.
