# 04-71 Wave B2: copy-on-write clones and content reuse

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. Technical design: `plan/design/perf.md` (Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest**. Core guarantees: `plan/design/folder.md`. Stage notes with APIs of merged tasks: bottom of `plan/04-perf.md`.

## Change
Implement rows 04-40 and 04-41 of the table «Задачи реализации» in `plan/design/perf.md`, section R16.
- **Clone primitives (04-40):** clone into a unique tmp through rooted paths / fd APIs with verified parents: macOS APFS `clonefileat`/`fclonefileat`, Linux `ioctl FICLONE`; if no safe clone API applies, a bounded copy from the held fd (never an absolute unsafe path). Unsupported / cross-device → bounded copy; other I/O errors are returned, not hidden. The source is never replaced by a hardlink; changing the clone never changes the source. The clone is verified by hash and goes through G1 like any prepared file.
- **Hash reuse in Apply (04-41):** an in-memory index hash → live canonical names (kept consistent with publishes/deletes). Before fetching a body, check a local candidate fd with stableHash and Exec separately: if the target already has the content, no body is fetched but Vector/Exec still go through the durable group commit; otherwise clone/copy a matching local file into the tmp instead of downloading. Candidate changed during the check → fall back to the network fetch.
Tests: the scenarios of both table rows (CoW source unchanged, cross-device copy, nofollow, unsupported fallback, target equal no fetch, candidate changed, Exec-only, permissions) and a harness scenario: syncing 200 files whose content already exists under other names fetches no bodies (count requests) and the result is byte-identical.

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O, directory walks or hashing under scanMu/mu (the post-capture hash inside the commit stays under the lock by design).
- A transient error (ReadDir/stat/hash/watch failure) never turns into a delete, a tombstone or data loss; a durability error never means success.
- Keep every stage 02/04 guarantee: rooted fd / no-follow, NFC, no-replace, capture, recovery before Scan/watcher/network, durable empty/changed-root latch.
- List in the commit messages the competing paths you checked (see «Конкурирующие пути» in perf.md: watcher/incremental/full Scan, downloads and several runPeer, group commit vs local writer, pause, rebind/confirm/leases, restart).

- The 04-62 harness (`SHAREDIR_PERF=1 go test -run Perf ./internal/app/`) must stay green; report its numbers before/after in worker_done.

- Budget: up to ~1200 lines including tests.

## Lead workflow (mandatory — you are the LEAD, not the implementer)
Smart model plans, light model implements, smart model reviews. The coordinator does not take part.
1. Plan (cheap, most important): read this spec and the design, then write `plan/specs/04-71.plan.md` — files and functions to add/change, signatures, data flow, invariants and lock order, exact test list with scenarios, and pitfalls. Precise enough that a weaker model cannot go in the wrong direction. Commit it.
2. Delegate: run `plan/tools/lead.sh 04-71 implement`, or, if the plan splits into parts with disjoint files, up to 3 parallel parts (`plan/tools/lead.sh 04-71 part <name> <part.md>` each, then `plan/tools/lead.sh --wait-all <dispatches>`; parts do not commit — you run the full acceptance and commit). A large plan may also be delivered as sequential phases (one `implement` per committed phase plan, at most 3). A luna worker implements the plan in this worktree, runs acceptance, commits and reports. Exit code 3: answer its question (`orca orchestration reply --id <id> --body ...`) if it asked one, then re-run `plan/tools/lead.sh --wait <dispatch>`.
3. Review: run the acceptance commands yourself, then the cheap first pass `plan/tools/self-review.sh 04-71` (Gemini), then review the whole diff yourself (correctness, races, durability, plan conformance, tests really testing the claims). Reject Gemini findings that contradict the spec or the owner decisions.
4. Fix rounds: if changes are needed, write the notes to a file under `$(git rev-parse --git-dir)/` and run `plan/tools/lead.sh 04-71 fix <N> <file>` (N = 1, then 2). At most 2 fix rounds.
5. Never end your turn while a child worker (implementer or reviewer) is running: Orca does not wake you when it reports. On exit code 3 immediately re-run the `--wait` command.
6. Takeover: if after 2 fix rounds the review still does not pass, finish the task yourself (that is the safety net against endless iterations).
7. worker_done: plan file, number of implementer/fix rounds, whether you took over, every finding (Gemini and yours) with its disposition, acceptance results.
