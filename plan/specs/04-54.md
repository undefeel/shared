# 04-54 perf harness

## Target
Project sharedir: two-way sync of one folder between macOS and Linux. Go daemon (`cmd/sharedir`, `internal/*`), macOS menu bar app (`macos/SharedirBar`), Omarchy widget (`omarchy/sharedir`). Stage 04 makes sync faster and reduces SSD writes. The technical design is `plan/design/perf.md` (written in Russian); its first section «Решения владельца по проекту» (owner decisions) **overrides the rest of the text**. Existing core guarantees: `plan/design/folder.md`.

This task is row **04-54** of the table «Задачи реализации» in `plan/design/perf.md`. Read these sections: «Пороги приёмки R20», «Общие инварианты», «Решения владельца по проекту».

## Change
Goal: perf harness — implement exactly what the design specifies for this task.
Required tests (from the design): two app.Daemon 2092 files, real flush counters, 1000/2000/4000 scaling.
- If the task touches flushing: owner decision item 1 applies — one `F_FULLFSYNC` per device per group phase, not per file; files and directories get a plain fsync.
- A correct alternative implementation must pass the tests: assert observable behaviour (data, phase order, hook counters), not internal function names.
- In wave A the harness covers only R1/R2/R11/R13 (group commit, journal, parallel downloads, retry). R16 and R5 scenarios are not required (the coordinator dropped the 04-39/04-49/04-51 dependencies). Thresholds: owner decision item 1 (recomputed R20).

## Constraints
- No new external dependencies (stdlib and the already used `golang.org/x/sys` only).
- Lock order scanMu → saveMu → mu; no network I/O or hashing under scanMu/mu.
- A transient I/O error never turns into a delete, a tombstone or data loss; a durability error never means success.
- List in the commit message the competing paths you checked (watcher, Scan, multiple runPeer/downloads, pause/rebind/confirm, restart).
- If you change a number or a rule, grep for it in `README.md`, `docs/`, `plan/design/perf.md` and report mismatches in worker_done (docs are updated by 04-56/04-57).
- Keep the diff within ~300 lines including tests; if it does not fit, stop and `ask` instead of growing the task.
- Communicate in English (questions, worker_done).
