# 01-01 Ревью: сеть и криптография

## Target
Проект sharedir: двусторонняя синхронизация одной папки между macOS и Linux. Go-демон (`cmd/sharedir`, `internal/*`). Обнаружение — UDP-броадкаст в LAN (порт 22101), передача — взаимный TLS 1.3 на 22100, ID устройства = SHA-256 сертификата, подключаться может только явно сопряжённое устройство. Есть relay через свой VPS для связи через интернет. Конфликты: побеждает более поздняя правка, другая сохраняется как `имя.sync-conflict-ДАТА-ВРЕМЯ-УСТРОЙСТВО.ext`. Подробности — `README.md`.

Область ревью (только чтение): `internal/identity/`, `internal/transport/`, `internal/discovery/`, `internal/relay/` (client.go, relay.go, server.go), `internal/app/relay.go`, `cmd/sharedir/relay.go`, `deploy/sharedir-relay.service`. Смежный код (`internal/app/daemon.go`, `internal/config/`) читай, чтобы понять вызовы, но находки в нём отмечай, только если они про сеть.

## Change
Найди уязвимости и баги в сетевой части. Обязательно проверь:
- Проверка пира в TLS: действительно ли сверяется отпечаток с сопряжёнными ID, нельзя ли подключиться с чужим сертификатом, нет ли `InsecureSkipVerify` без собственной проверки, версия TLS, срок и генерация ключа, права на файл ключа.
- Сопряжение: можно ли навязать себя в сопряжение, подменить ID через UDP-анонс, отравить адрес пира (перенаправление на чужой хост, амплификация, огромные пакеты).
- Протокол кадров: лимиты размера сообщений и путей, чтение без ограничения (`io.ReadAll`, длина из сети), таймауты, утечки горутин и соединений при обрыве.
- Relay: что видит и может сделать VPS или посторонний клиент — авторизация до сессии, связывание двух сторон, сквозной ли TLS между устройствами (relay не должен читать данные), DoS (лимиты подключений, память), переход relay → прямая связь без потери проверки пира. Песочница systemd в `deploy/sharedir-relay.service`.

## Constraints
- Это ревью: **исходный код не меняй**. Единственный файл, который ты создаёшь и коммитишь, — `plan/reviews/01-01.md`.
- Чтобы подтвердить находку, можно писать временные тесты и запускать их (`go test -race -run … ./internal/…`), но перед коммитом удали их. Код репро-теста вставь в отчёт.
- Включай только то, что подтверждено кодом (конкретный путь исполнения) или запуском. Догадки без пути исполнения — в отдельный раздел «Под вопросом», не больше 5 пунктов.
- Стиль и вкусовщину не пиши. Нужны баги, гонки, потеря данных, уязвимости, неверная обработка ошибок с реальными последствиями.
- Проверь все конкурирующие пути: горутины, повторные подключения, одновременные правки на двух машинах, обрыв посреди передачи, рестарт демона.
- Отчёт — на русском языке.

## Формат отчёта `plan/reviews/01-01.md`
Находки отсортированы по серьёзности. Каждая — отдельный раздел:

```
### 01-01-NN [critical|high|medium|low] Короткое название
- Где: path/to/file.go:LINE (и другие места)
- Сценарий: входные данные / состояние → что происходит не так (конкретно)
- Доказательство: путь исполнения по строкам или репро-тест (код + вывод)
- Исправление: что поменять, какие файлы задеты
- Уровень исправления: L1|L2|L3 (L1 — локально, решение очевидно; L2 — логика в 1–2 модулях; L3 — несколько модулей, конкурентность, протокол)
```

В конце — таблица «ID | серьёзность | файл | уровень» и раздел «Под вопросом».

## Observable acceptance
```
test -s plan/reviews/01-01.md
git diff --stat main -- . ':!plan'        # пусто: исходники не тронуты
go vet ./... && go test -race ./... 2>&1 | tail -20   # зелёный, как и до ревью
```
Закоммить отчёт одним коммитом `review: 01-01`. Ненулевой выход команд приёмки = задача провалена.
